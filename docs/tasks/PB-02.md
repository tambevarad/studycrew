## Build

**Service** `src/server/services/profile/service.ts`
- `getProfile(userId): Promise<ProfileDTO>` — 404 if missing.
- `updateProfile(userId, input: UpdateProfileInput): Promise<ProfileDTO>` — trims, de-duplicates courses (after
  normalization) and skills (case-insensitive), keeps order. Email is not editable.

**Routes** `GET /api/v1/me/profile`, `PATCH /api/v1/me/profile` with `authedRoute`.

**Pages**
- `/profile`: `PageHeader` "Your profile". Form sections: Basics (name, email read-only), Time zone (select of
  `Intl.supportedValuesOf("timeZone")` with the browser's zone suggested — "Detected: America/Chicago · Use this"),
  Courses (chip input: type `cse6324`, Enter → shows "CSE 6324"; remove with ×; max 12), Skills (chip input, max 20),
  Bio (textarea, 500 chars with counter). Save button disabled until something changes; success toast "Profile saved".
  Field errors under fields. Link to "Edit my availability" → `/availability`.
- Sign-up: name, email, password (show/hide toggle, ≥ 8 chars, live hint), timezone auto-detected and sent. Errors:
  duplicate email → "An account with that email already exists. Sign in instead?" with link. After sign-up → `/profile?welcome=1`
  showing an Alert "Welcome! Add your courses so teammates can find you."
- Sign-in: keep `?next=` redirect support; friendly wrong-password message (exists); disable button while pending.
- Signed-in users visiting `/sign-in` or `/sign-up` are redirected to `/dashboard`.

## Acceptance criteria

- AC1: Given a new email, when I sign up with name, email, and an 8+ char password, then I'm signed in and land on my profile with the welcome message.
- AC2: Given an existing email, when I sign up, then I see "An account with that email already exists" and no account is created.
- AC3: Given my account, when I sign in with a wrong password, then I see a friendly error and stay on the page; with the right password I reach the dashboard.
- AC4: Given I'm signed in, when I sign out, then protected pages redirect me to sign-in.
- AC5: When I add courses `cse6324` and `CSE 6324`, then my profile stores one course "CSE 6324".
- AC6: When I pick a time zone and save, then `GET /api/v1/me/profile` returns it and dates elsewhere render in it.
- AC7: Invalid input (empty name, 21 skills, bad time zone) returns 400 with field errors shown under the fields.
- AC8 (NFR-02): the password is stored only as a hash (`account.password` ≠ plain text); the session cookie is HttpOnly + SameSite=Lax.
- AC9 (NFR-03): profile and auth pages have no serious/critical axe violations and work keyboard-only.

## Implementation notes (owner fills in)

**Built (Oct 22, Krish + Claude Code):**

- **Service** `src/server/services/profile/service.ts`: `getProfile`, `updateProfile` (partial update; only sent
  fields change; empty bio → `null`; email can't be changed because the contract strips it). Pure helpers in
  `normalize.ts`: `dedupeCourses` (normalize + de-dupe, keeps order), `dedupeSkills` (trim, case-insensitive de-dupe,
  keeps the first spelling).
- **Routes** `GET/PATCH /api/v1/me/profile` with `authedRoute`.
- **Profile page** `/profile`: Basics (email read-only), Time zone (select + "Detected: … · Use this"), Courses and
  Skills chip inputs (Enter or comma adds, × or Backspace removes, limits 12 / 20 with counts, duplicate message),
  Bio with a character counter. Save is disabled until something changes; "Undo changes" restores the saved values.
  `?welcome=1` shows the welcome Alert. "Edit my availability" links to `/availability`.
- **Auth form**: client-side field errors under each field (`validation.ts`), show/hide password toggle, live
  "N more characters needed" hint, duplicate email → "An account with that email already exists. Sign in instead?",
  429 → "Too many attempts…". `?next=` is kept between sign-in and sign-up and only same-site paths are followed
  (`safeNextPath`, blocks `//evil.com`). After sign-up → `next` if present, else `/profile?welcome=1`.
- **(auth) layout** redirects signed-in users to `/dashboard`.

**Decisions / gotchas:**

- The time-zone list is computed on the server and passed to the form. Browsers and Node return different
  `Intl.supportedValuesOf("timeZone")` lists, which caused a hydration error (React #418) when computed on the client.
- The browser's zone is read with `useSyncExternalStore` (null on the server) so there is no hydration mismatch.
- Better Auth limits sign-in to 3 attempts per 10 s per IP in production. The old form showed "don't match" for every
  error, which hid this; the form now shows the real reason. `auth.cy.ts` waits 10 s at the end so the next spec
  isn't rate-limited.
- **Contract request** `docs/contract-requests/PB-02-toast-contrast.md`: sonner's `richColors` success toast is 4.25:1
  (axe serious). `auth.cy.ts` runs the axe check after the toast closes until the shared `Toaster` is fixed.

**Tests:** `tests/unit/profile.test.ts` (normalization, chip rules, auth validation, safe `next`),
`tests/integration/profile.test.ts` (service, routes, AC5–AC8 incl. hash + cookie flags via `auth.handler`),
`cypress/e2e/auth.cy.ts` (AC1–AC5, AC9).

**Follow-up (Oct 22, after #23 merged): rate limit**

- **Real retry time in the 429 message.** The form reads Better Auth's `X-Retry-After` through `fetchOptions.onError`
  (`result.error` carries no headers) and shows "Too many attempts. Try again in 8 seconds." Pure helpers
  `retryAfterSeconds` / `rateLimitMessage` in `validation.ts` are unit-tested. The old text said "Wait a minute", but the
  window is 10 s.
- **`auth.cy.ts` no longer flakes on the limit.** Better Auth keys the limit by IP + path: 3 sign-ins and, separately,
  3 sign-ups per 10 s, shared with every spec's `cy.login()`. The spec's UI submits go through
  `submitWaitingOutRateLimit()`: if the response is 429, it checks the message, waits exactly `X-Retry-After`, and submits
  again. The blind 10 s `after()` wait is gone (`cy.login()` retries on 429 since #20). A new test trips the limit on
  purpose and checks "Try again in N seconds."
- `smoke.cy.ts` has the same problem in a shared file: `docs/contract-requests/PB-02-smoke-ui-sign-in-rate-limit.md`.
